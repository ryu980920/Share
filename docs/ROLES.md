# 역할 분담 · 격자 분할 · 일정

> **설계 원칙**: 3인 전원이 첫날부터 마지막 날까지 **구조 생성 → 시뮬레이션 실행 → 결과 정리**의 전체 사이클을 돈다.
> 나뉘는 것은 *작업 종류*가 아니라 *격자 위의 좌표*다. (기존 BCAT 3인 체제의 설계 원칙을 그대로 승계)

> **2026-08-04/05 프레이밍 전환**: 이 프로젝트는 처음엔 People-Bean/Luryi-Suhir 결함 경계(trade-off boundary) 지도를 목표로 했으나, 실제 baseline 치수(fin 반폭 7.5nm)에서 Ge 42~100% 전 구간이 이론상 "무제한 보호"로 계산되어 그 프레이밍을 폐기하고 **Stress Transfer Efficiency(STE, 응력 전달 효율)** 로 전환했다. 아래 격자 분할 원칙(세로 3등분, 교차검증)은 이전과 동일하게 유지되지만, **축 이름(리세스 깊이 → FR)과 지표(mobility_gain_pct → ste)가 바뀌었다.** 자세한 경위는 [README.md](../README.md) 참고.

## 1. 팀 구성 — 3인 (유용성 · 주수빈 · 남다연)

프로젝트는 구조/물리/분석 3역할 분담이 아니라 **"2차원 격자를 세로로 3등분"**하는 방식이다. 이전에 2인 체제로 잠깐 운영됐던 시기가 있었으나(devlog.md 참고), 주수빈이 다시 합류하면서 원래의 3인 체제로 돌아왔다.

- 격자를 **세로로 3등분**(열 기준 3분할)한다 — 이미 검증됐던 병렬화 방식.
- 담당 열이 가운데(공칭 Ge% 50% 포함)인 사람이 인접 열 2개와 모두 경계를 맞대므로, 교차검증에서 그 사람이 두 번 관여한다 (2절).
- 대시보드 과제 카드는 **공동(joint) 과제**와 **개별(solo) 과제**를 구분한다. 공동 과제는 체크박스 3개(각자 자기 완료 여부 표시), 개별 과제는 체크박스 1개(담당자 본인).

## 2. DoE 격자 — ⚠ 스윕 값 미확정

**X축 — Ge 조성(%)**: 예제 스크립트에 `GeMoleFraction` 으로 **이미 파라미터화돼 있다.** 공칭값 50%(baseline). 스윕 레벨(몇 %부터 몇 %까지, 몇 단계)은 아직 팀이 확정하지 않았다.

**Y축 — FR (리세스 깊이, fin 바닥 아래 방향, nm)**: **⚠ 스크립트에 아직 없는 변수다.** Esd(S/D-채널 가로 근접거리) 파라미터화 방식을 참고해 신규로 추가해야 한다 — 정확한 문법 미확인. 전원 공동 과제(P0 #1, 5절 W1 일정 참고)로 최우선 처리한다. 이게 확인되기 전까지는 Y축 스윕 자체를 시작할 수 없다 — **이번 프로젝트 최우선 게이트.**

격자 크기(몇×몇)는 두 축의 스윕 값이 정해져야 같이 정해진다. 참고로 BCAT 프로젝트는 5×5=25점(3인)이었다 — **x_levels 개수를 3의 배수로 잡으면** 아래 열 분할이 딱 떨어진다. 최종 크기는 아래 W1 게이트 항목들이 끝난 후 팀이 결정한다.

**열(column) 기준 3분할** — Ge% 값이 확정되면, 낮은 1/3 열을 주수빈, 중간 1/3 열을 유용성, 높은 1/3 열을 남다연이 담당한다. 유용성의 열에는 공칭(baseline, Ge% 50%) 이 포함된다 — 프로젝트의 축이 되는 부분이라 유용성이 직접 맡기로 함.

| 담당 | 담당 열 | 올릴 파일 | 추가 과제 |
|---|---|---|---|
| **주수빈** | Ge% 낮은 1/3 | `runs/주수빈_G<낮은열>.csv` | Sentaurus 버전/라이선스 옵션 확인 |
| **유용성** | Ge% 중간 1/3 (공칭 50% 포함) | `runs/유용성_G<중간열>.csv` | Choi 2012 원 논문 응력 데이터 직접 확인 + STE 개념 재검증 |
| **남다연** | Ge% 높은 1/3 | `runs/남다연_G<높은열>.csv` | 메쉬 수렴성 검증 + STE 정규화 지점(채널 인접 정의) 후보 조사 |

공칭(baseline) 격자점 = Ge% 50%, FR ⚠ TODO(스윕값 확정 전엔 원본 예제 상태, FR=0 에 해당하는지부터 확인 필요). 확정되면 전원이 독립적으로 돌려 서로 대조한다 (Phase 0 게이트).

### 교차검증 규칙 (필수)

열이 3개(낮은/중간/높은)라 서로 **인접한 쌍끼리만** 경계를 맞댄다. 따라서 중간 열 담당인 유용성이 양쪽 다 교차검증한다.

| 담당 | 추가 실행 | 대조 상대 | 올릴 파일 |
|---|---|---|---|
| 주수빈 | 경계 열 1점 (유용성 쪽) | 유용성 | `runs/주수빈_교차검증.csv` |
| 유용성 | 경계 열 2점 (주수빈 쪽 1점 + 남다연 쪽 1점) | 주수빈, 남다연 | `runs/유용성_교차검증.csv` |
| 남다연 | 경계 열 1점 (유용성 쪽) | 유용성 | `runs/남다연_교차검증.csv` |

같은 `run_id` 가 두 파일에 있으면 **`build.py` 가 자동으로 편차를 계산**해 알려준다.
**5% 이상 차이나면 즉시 Issue 를 연다.** 환경 차이(버전, STE 정규화 방식, 모델 파라미터)가 있다는 뜻이고,
이걸 놓치면 지도가 통째로 거짓말이 된다. 주수빈과 남다연은 열이 안 붙어 있어 직접 대조할 필요는 없다.

## 3. 제출물 — 데이터만이 아니다

격자점 하나를 완료할 때 올리는 것은 세 가지다. 자세한 절차는 [runs/README.md](../runs/README.md), 첨부물 폴더 예시는 `runs/attachments/_예시`.

1. **수치 데이터** — `runs/<이름>_<스윕이름>.csv` 에 누적. 컬럼은 `run_id, stress_GPa, ste` (★ ste 컬럼명 제안 — 팀 확정 필요, README.md 참고)
2. **소자 사진** — Ge%/FR 을 바꾸며 뭐가 달라졌는지 보여주는 사진 (구조 단면 등 무엇이든 상관없고 여러 장 올려도 된다). `runs/attachments/<run_id>/` 아래에 파일명 자유롭게 저장
3. **메모** — `runs/attachments/<run_id>/notes.md` 에 자유 형식으로: 어떤 변수를 바꿨는지, 무엇이 이상했는지, 다음에 수정할 게 있는지

`build.py` 는 사진 파일 개수와 `notes.md` 존재 여부만 확인해 대시보드에 표시한다 (내용을 읽어서 검증하진 않는다).

**대시보드(`index.html`)에서 GitHub 연동 후 직접 업로드하면 편하다** — 격자 칸(또는 Run ID 직접 입력)을 클릭하면 사진 업로드 + 메모 작성을 바로 할 수 있다.

> **공통(joint) 과제는 이 절차가 필요 없다.** 논문 정독, baseline 구조 확정 같은 공동 과제는 파일 제출 없이 체크박스로만 완료를 표시한다.

## 4. 개별 추가 과제 — 잡무가 아닌 이유

| 담당 | 실험 | 내용 | 산출물 |
|---|---|---|---|
| 유용성 | Choi 2012 원 논문 응력 데이터 직접 확인 + STE 개념 재검증 | 근접효과 데이터(nested −1289MPa vs isolated +53MPa)와 "Stress Transfer Efficiency" 용어 사용 맥락을 원문에서 직접 대조 — 우리 정의와 같은지 다른지 판단 (지어내지 않는다) | `docs/model_choice.md` |
| 주수빈 | Sentaurus 버전/라이선스 옵션 확인 | 설치된 버전과 라이선스로 실제 켜져 있는 모듈 확인. Stress/Mechanical 관련 옵션이 별도 라이선스인지도 확인 | `docs/license_check.md` |
| 남다연 | 메쉬 수렴성 검증 + STE 정규화 지점 후보 조사 | 리세스-채널 계면 국소 메쉬를 성김/중간/촘촘 3단계로 두고 응력 값 변화 측정. 동시에 "채널 인접"으로 볼 만한 후보 지점 2~3개(좌표 기준)를 제안해, 팀이 STE 정규화 방법을 확정할 때 근거자료로 쓴다 | 수렴 그래프 + 후보 지점 제안서 |

> ⚠ 이전 버전(결함 경계 프레이밍)에 있던 "소성완화 모델 확인 + People-Bean 근사식 검증"(유용성), "fin 폭 확정"(남다연) 과제는 **이번 전환으로 제거됐다.** fin 폭은 이미 baseline 스펙(fin 반폭 7.5nm)으로 확정됐고, 결함 모델 확인은 더 이상 이 프로젝트의 핵심 질문이 아니기 때문이다.

발표 Q&A 에서 "FR 변수는 왜 스크립트에 없었나요?", "메쉬는 충분한가요?", "STE 정규화 방법의 근거는 무엇인가요?"는 거의 확실히 나오는 질문이다. 이 결과가 그 답변의 근거이고, 심사 항목 '완성도'에 직접 연결된다.
