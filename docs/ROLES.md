# 역할 분담 · 격자 분할 · 일정

> **설계 원칙**: 3인 전원이 첫날부터 마지막 날까지 **구조 생성 → 시뮬레이션 실행 → 결과 정리**의 전체 사이클을 돈다.
> 나뉘는 것은 *작업 종류*가 아니라 *격자 위의 좌표*다. (기존 BCAT 3인 체제의 설계 원칙을 그대로 승계)

---

## 1. 팀 구성 — 3인 (유용성 · 주수빈 · 남다연)

프로젝트는 구조/물리/분석 3역할 분담이 아니라 **"2차원 격자를 세로로 3등분"**하는 방식이다. 이전에 2인 체제로 잠깐 운영됐던 시기가 있었으나(devlog.md 참고), 주수빈이 다시 합류하면서 원래의 3인 체제로 돌아왔다.

- 격자를 **세로로 3등분**(열 기준 3분할)한다 — 이미 검증됐던 병렬화 방식.
- 담당 열이 가운데(공칭 Ge% 포함)인 사람이 인접 열 2개와 모두 경계를 맞대므로, 교차검증에서 그 사람이 두 번 관여한다 (2절).
- 대시보드 과제 카드는 **공동(joint) 과제**와 **개별(solo) 과제**를 구분한다. 공동 과제는 체크박스 3개(각자 자기 완료 여부 표시), 개별 과제는 체크박스 1개(담당자 본인).

**Y축 — 리세스 깊이(nm)** : ⚠ TODO — 마찬가지.

격자 크기(몇×몇)도 스윕 값이 정해져야 같이 정해진다. 참고로 BCAT 프로젝트는 5×5=25점(3인)이었다 — **x_levels 개수를 3의 배수로 잡으면** 아래 열 분할이 딱 떨어진다. 최종 크기는 #1 과제 완료 후 팀이 결정한다.

**열(column) 기준 3분할** — Ge% 값이 확정되면, 낮은 1/3 열을 유용성, 중간 1/3 열을 주수빈, 높은 1/3 열을 남다연이 담당한다. 주수빈의 열에는 공칭(baseline) Ge% 가 포함된다.

| 담당 | 담당 열 | 올릴 파일 | 추가 과제 |

| **주수빈** | Ge% 중간 1/3 (공칭 포함) | `runs/주수빈_G<중간열>.csv` | Sentaurus 버전/라이선스 옵션 확인 |
| **남다연** | Ge% 높은 1/3 | `runs/남다연_G<높은열>.csv` | 메쉬 수렴성 검증 + Luryi-Suhir 보정용 fin 폭 확정 |

### 교차검증 규칙 (필수)

열이 3개(낮은/중간/높은)라 서로 **인접한 쌍끼리만** 경계를 맞댄다. 따라서 중간 열 담당인 주수빈이 양쪽 다 교차검증한다.

| 담당 | 추가 실행 | 대조 상대 | 올릴 파일 |
|---|---|---|---|
| 유용성 | 경계 열 1점 (주수빈 쪽) | 주수빈 | `runs/유용성_교차검증.csv` |
| 주수빈 | 경계 열 2점 (유용성 쪽 1점 + 남다연 쪽 1점) | 유용성, 남다연 | `runs/주수빈_교차검증.csv` |
| 남다연 | 경계 열 1점 (주수빈 쪽) | 주수빈 | `runs/남다연_교차검증.csv` |

같은 `run_id` 가 두 파일에 있으면 **`build.py` 가 자동으로 편차를 계산**해 알려준다.
**5% 이상 차이나면 즉시 Issue 를 연다.** 환경 차이(버전, 정규화 방식, 모델 파라미터)가 있다는 뜻이고,
이걸 놓치면 등고선이 통째로 거짓말이 된다. 유용성과 남다연은 열이 안 붙어 있어 직접 대조할 필요는 없다.

## 3. 제출물 — 데이터만이 아니다

격자점 하나를 완료할 때 올리는 것은 세 가지다. 자세한 절차는 [runs/README.md](../runs/README.md), 첨부물 폴더 예시는 `runs/attachments/_예시`.

1. **수치 데이터** — `runs/<이름>_<스윕이름>.csv` 에 누적 (기존 방식과 동일)
2. **소자 사진** — Ge%/리세스를 바꾸며 뭐가 달라졌는지 보여주는 사진 (구조 단면, Id-Vg 커브 등 무엇이든 상관없고 여러 장 올려도 된다). `runs/attachments/<run_id>/` 아래에 파일명 자유롭게 저장
3. **메모** — `runs/attachments/<run_id>/notes.md` 에 자유 형식으로: 어떤 변수를 바꿨는지, 무엇이 이상했는지, 다음에 수정할 게 있는지

`build.py` 는 사진 파일 개수와 `notes.md` 존재 여부만 확인해 대시보드에 표시한다 (내용을 읽어서 검증하진 않는다).

**대시보드(`index.html`)에서 GitHub 연동 후 직접 업로드하면 편하다** — 격자 칸(또는 Run ID 직접 입력)을 클릭하면 사진 업로드 + 메모 작성을 바로 할 수 있다. 대시보드는 Ge%/리세스 값을 보고 People-Bean 임계두께에 가까운 조건인지 판단해서, 그런 경우 결함(전위) 흔적이 보이는 사진을 남기라고 안내 문구로 알려준다.

> **공통(joint) 과제는 이 절차가 필요 없다.** 논문 정독, baseline 구조 확정 같은 공동 과제는 파일 제출 없이 체크박스로만 완료를 표시한다.

## 4. 개별 추가 과제 — 잡무가 아닌 이유

| 담당 | 실험 | 내용 | 산출물 |
|---|---|---|---|
| 유용성 | 소성완화 모델 확인 | Sentaurus Stress 섹션에 전위결함 예측 모델이 있는지 학교 라이선스 매뉴얼로 확인. 없다고 확인되면 하이브리드 방법론(경계선 오버레이)이 유일한 선택지임을 문서화 | `docs/model_choice.md` |
| 유용성 | People-Bean 근사식 검증 | Tc≈1.23x⁻³·⁰⁸ 근사식을 원 논문(1985) 그래프와 대조해 오차 범위 확인 | 오차 비교 표 |
| 주수빈 | Sentaurus 버전/라이선스 옵션 확인 | 설치된 버전과 라이선스로 실제 켜져 있는 모듈(특히 Stress 관련) 확인. 유용성의 "모델 유무 확인" 결과와 대조해 실제로 쓸 수 있는지까지 검증 | `docs/license_check.md` |
| 남다연 | 메쉬 수렴성 검증 | 리세스-채널 경계부 국소 메쉬를 성김/중간/촘촘 3단계로 두고 응력 값 변화 측정 | 수렴 그래프 |
| 남다연 | fin 폭 확정 | FinFET_14nm/22nm 예제의 실제 fin 폭을 확인해 Luryi-Suhir 보정식(W<15×Tc)에 대입 | `baseline/params.yaml` PR |

발표 Q&A 에서 "왜 그 방법론을 썼나요?", "메쉬는 충분한가요?", "라이선스로 실제 그 모델을 쓸 수 있나요?"는 거의 확실히 나오는 질문이다. 이 결과가 그 답변의 근거이고, 심사 항목 '완성도'에 직접 연결된다.
